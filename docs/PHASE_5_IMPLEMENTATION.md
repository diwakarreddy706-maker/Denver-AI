# Denver AI Assistant — Phase 5: Desktop Automation & System Control

## 1. Architecture Overview

Phase 5 introduces **Denver Desktop Automation & System Control**, providing secure, Windows-native desktop management while strictly preserving the existing architecture, security boundaries, and pipeline invariants established across Phases 0–4.

### The Non-Negotiable Execution Flow
Neither AI providers nor the voice subsystem ever possess direct operating system execution authority. Every user request (whether originating from CLI text, the API, or voice transcription) is routed through the strict pipeline:

```text
User Input (Text / Voice Transcript)
              ↓
    CommandEngineService
              ↓
        IntentRouter
              ↓
      SafetyValidator (Deny-by-default, allowlist & pattern inspection)
              ↓
       ActionRegistry
              ↓
     AutomationExecutor (Coordinates sub-controllers & confirmation gate)
              ↓
  Safe Allowlisted Controller (ctypes Win32 / pycaw / mss / psutil / webbrowser)
              ↓
    Structured AutomationResult
              ↓
        Denver Response
```

### Prohibited Mechanisms
The following are strictly banned throughout the codebase and verified through automated security tests:
- `eval()` and `exec()`
- `os.system()`
- Unrestricted `subprocess` invocations
- Arbitrary shell/PowerShell command execution generated by LLMs or users
- Arbitrary executable paths supplied by users/LLMs
- Unrestricted pixel/keyboard automation
- Hidden background execution bypassing the `SafetyValidator` or `ActionRegistry`

## 4. Risk Levels & Safety Model

Every action is statically classified with an `AutomationRisk`:

| Risk Level | Actions Included | Enforcement Behavior |
|---|---|---|
| **SAFE** | `get_cpu`, `get_ram`, `get_battery`, `get_volume`, `get_system_summary`, `get_system_status` | Immediate execution. |
| **LOW** | `open_application`, `open_browser` | Allowlist validated, executed immediately. |
| **MEDIUM** | `close_application`, `minimize_window`, `maximize_window`, `restore_window`, `focus_window`, `show_desktop`, `set_volume`, `increase_volume`, `decrease_volume`, `mute_volume`, `unmute_volume`, `take_screenshot` | Validated target, executed immediately. |
| **HIGH** | `lock_workstation`, `shutdown` *(unimplemented)*, `restart` *(unimplemented)* | Intercepted; generates a 30-second single-use confirmation token (`cnf_*`). |

AI providers and user utterances cannot downgrade risk classifications.

## 5. Confirmation Mechanism

When a high-risk action (e.g. `lock_workstation`) is requested:
1. `AutomationExecutor` checks `ConfirmationManager`.
2. If no valid token is provided, a pending request is registered with an expiration timestamp (`now + 30s`).
3. An `AutomationConfirmationRequired` event is published to the `EventBus`, and a structured response is returned:
   ```json
   {
     "success": true,
     "message": "Locking your workstation requires confirmation. Proceed?",
     "action": "lock_workstation",
     "data": { "confirmation_token": "cnf_0fa8db92", "expires_at": 1789373477.18 }
   }
   ```
4. When the user responds with `"Denver, confirm"` or `"yes"`, `confirm_action` consumes the exact token.
5. The token is immediately invalidated (single-use) to prevent replay attacks, and the pending action executes.
6. If 30 seconds elapse without confirmation, the pending token expires automatically.

## 6. Windows APIs & Native Integration

- **Win32 UI Automation**: Implemented using Python's standard `ctypes.windll.user32` and `ctypes.windll.kernel32`:
  - `EnumWindows` + `GetWindowTextW` for window enumeration without pixel coordinates.
  - `ShowWindowAsync` with `SW_MINIMIZE` (6), `SW_MAXIMIZE` (3), `SW_RESTORE` (9).
  - `SetForegroundWindow` for focusing applications safely.
  - `LockWorkStation` for locking the active session.
- **Audio Control**: Uses Windows Core Audio COM endpoints (`IAudioEndpointVolume`) via `pycaw`.
- **Screen Capture**: Uses `mss` for monitor frame capture to PNG.
- **System Metrics**: Uses `psutil` + standard `platform` libraries.

---

## 7. URL Safety & Web Protection

All URLs passed to `open_browser` are validated via `BrowserController.validate_url()`:
- Allowed protocols: `https://`, `http://`.
- Forbidden protocols: `file://`, `javascript:`, `data:`, `vbscript:`, `about:`.
- Shell injection prevention: Characters such as `|`, `&`, `;`, `\n`, `\r`, `\x00` are strictly rejected.
- File path & drive injection prevention: Local file paths and drive specifiers (e.g. `C:\`, `\\unc\`) are rejected.
- Known site catalog automatically expands shortcuts (e.g. `"youtube"` -> `"https://www.youtube.com"`).

---

## 8. Filesystem Safety

- Screenshots and generated assets are written exclusively to `screenshot_directory` (defaults to `data/screenshots/`).
- Resolves all paths using `Path(target).resolve()`.
- Explicitly tests and blocks directory traversal attempts (`../`, `..\`, absolute paths outside the target directory, UNC paths).
- Automatically creates the output folder on demand.

## 11. Configuration Settings

The following settings are exposed in `DenverSettings` (`src/denver/config/settings.py`):
- `DENVER_AUTOMATION_ENABLED`: Enable/disable automation (`true` by default).
- `DENVER_AUTOMATION_CONFIRMATION_TIMEOUT`: Expiration duration for high-risk actions in seconds (`30.0` by default).
- `DENVER_ALLOW_HIGH_RISK_ACTIONS`: Master switch for executing high-risk actions (`false` by default).
- `DENVER_DEFAULT_BROWSER`: Default browser target (`"default"`).
- `DENVER_SCREENSHOT_DIRECTORY`: Approved storage directory for screenshots (`"data/screenshots"`).

## 14. Python 3.14 Compatibility & Limitations

- **Runtime**: Python 3.14.7 on Windows 11 (`win32`).
- **Dependencies**: `pycaw`, `mss`, `psutil` are fully operational on Python 3.14.7.
- **Destructive Actions Scope**: `shutdown`, `restart`, and `logoff` were deliberately left unimplemented in this phase to prevent unintentional OS termination; they will be evaluated for future phases with multi-factor confirmations.
- **Keyboard / Mouse Automation**: Unrestricted pixel/keyboard automation is strictly prohibited and not implemented. All window manipulations use deterministic Win32 API handles and title matching.
